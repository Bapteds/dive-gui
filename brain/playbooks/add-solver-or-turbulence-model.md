# Playbook: Add a solver or a turbulence model

> When to use: offer a new ESI OpenFOAM v2406 solver binary in the Solver tab, change how a solver is scaffolded, or add a turbulence model to the setup wizard · Related: `brain/features/solver-and-runs.md` (§3 rules, §10 "to modify"), `brain/codemap/root-shared-mcp.md` (solver catalog, turbulence), `brain/codemap/api-projects.md` (`files.service.ts`, `runs.*`), `brain/codemap/api-lib.md` (`openfoamCase`), `brain/codemap/web-features-meshing-solver.md` (`features/solver`), `brain/known-issues.md` (M18, K29, K39) · Updated: 2026-09-28

## Before you start
- Read `brain/features/solver-and-runs.md` §3 and §10. The catalog is **data in `@dive/shared`**; the API and the web consume it, they never redeclare it.
- Production runs **ESI OpenFOAM v2406** (openfoam.com). Only classic binaries invoked as `<solver> -case <dir>` are valid. Never the OpenFOAM.org launcher (`foamRun -solver ...`): `foamRun` stays in `SOLVER_IDS` as a placeholder that is never runnable. Confirm the binary exists on the Debian server (`source "$OPENFOAM_BASHRC" && command -v <solver>`) and find its tutorial under `$FOAM_TUTORIALS` for the expected files.
- Decide with the user:
  - **Solver**: category (it drives family and tier, see step 1), regime (`steady` / `transient`), and whether the generic scaffold is acceptable. Today every non-RANS category gets the incompressible RANS file set (known issue **M18**): an `interFoam` case scaffolded that way is not physically complete. A solver that needs its own files (`alpha.water`, `p_rgh`, `g`, thermo...) is a feature: spec first (`brain/specs/YYYY-MM-DD-<topic>-design.md`).
  - **Turbulence model**: exact OpenFOAM token (`RASModel` / `LESModel` value), `simulationType`, the `0/` fields it reads, and whether it introduces a field name the app does not know yet.

## Steps: a solver
1. **Catalog** in `packages/shared/src/index.ts`:
   - add the id to `SOLVER_IDS`, inside its category group and before `foamRun`;
   - add a `SOLVER_LIBRARY` entry `{ id, label, summary, category, regime }` (library order = picker order).
   That is all the catalog needs: `SOLVER_CATALOG` is generated by `buildSolverSpec(info)`. Tier `full` if the category is in `FULL_TEMPLATE_CATEGORIES` (`incompressible`, `compressible`, `supersonic`), else `base`; family `compressible` if in `COMPRESSIBLE_CATEGORIES` (adds `thermophysicalProperties`, `0/T`, `0/alphat`, absolute `0/p`); no turbulence knob if in `NON_FLOW_CATEGORIES`. A new category also needs a `SOLVER_CATEGORIES` entry (display order) and a conscious choice for those three arrays.
2. **Validation follows automatically**: `scaffoldSolverSchema` (`apps/api/src/modules/projects/files.schemas.ts`) and `startRunSchema` (`runs.schemas.ts`) use `z.enum(SOLVER_IDS)`; `runs.service.ts` rejects a `controlDict` `application` outside `SOLVER_IDS` (422).
3. **Gate and scaffold** (`apps/api/src/modules/projects/files.service.ts`): `computeRunnable` takes the "configurable" branch for every library id (`isConfigurableSolver`), checks `requiredFilesForModel(SOLVER_CATALOG[id].requiredFiles, model)` and `systemNumericsNeedsRepair` on the `system/` trio. The "known but not configurable" branch is unreachable (**K39**): do not design around it. `scaffoldSolver` writes through `renderSolverFile`.
4. **Renderers** (`apps/api/src/lib/openfoamCase.ts`): `renderSolverFile(solver, path, patches, model)` switches only on `spec.family` and `spec.regime` (four `controlDict` / `fvSchemes` / `fvSolution` flavours: `simpleFoam*`, `pimpleFoam*`, `rhoSimpleFoam*`, `rhoPimpleFoam*`). A solver that needs different content means: a new family value in `SolverSpec.family`, its branch in `buildSolverSpec`, the new renderer cases, **and** the matching markers in `systemNumericsNeedsRepair` / `pFieldNeedsRepair`. Parity rule: whatever the renderer emits, the gate must recognise, otherwise a freshly scaffolded case reads "not runnable" or a second scaffold is not idempotent.
5. **New Easy parameter** (optional): declare a `SolverParamDef` constant next to `turbulenceParam` / `endTimeParam` (`key`, `label`, `help`, `kind`, `options`, `file`, `path`) and push it in `buildSolverSpec`. `file` + `path` must address what the renderer writes: `SolverEasyForm` (`features/solver/SolverConfigPanel.tsx`) splices the value with `setFoamValue` / `insertFoamField`.
6. **Web**: nothing to wire. `SolverBrowserDialog` groups `SOLVER_LIBRARY` by `SOLVER_CATEGORIES` and shows the `Guided` / `Base setup` badge from `SOLVER_CATALOG[id].tier`; `SolverSetupWizard` reads `regime` (LES with a steady solver shows a warning only). Types come through `apps/web/src/lib/api/types.ts` re-exports. The MCP server (`apps/mcp/src/server.ts`) takes solver and turbulence as free strings: nothing to change.

## Steps: a turbulence model
1. **Shared**: add a `TURBULENCE_MODELS` entry `{ id, label, summary, simulationType, fields }` in its approach group, and the same id to `TURBULENCE_MODEL_IDS` (hand-maintained tuple used by zod; 20 = 20 today, no test locks it: add one to `apps/api/tests/solverCatalog.test.ts` if you touch the list).
2. **Known field names only** (`k`, `epsilon`, `omega`, `nut`, `nuTilda`, `R`): everything else is derived. `turbulenceFieldsFor` drives the scaffold (writes exactly those `0/` fields, deletes the others from `0/` and `0.orig/`) and the gate (`requiredFilesForModel`); `transportedTurbulenceFields` (fields minus `nut`) drives the `div(phi,<field>)` lines, the linear-solver regex keys and the `residualControl` / `relaxationFactors` entries; `turbulenceWallBc` picks the wall function used by `fieldBcBody(field, 'wall', model)`; `renderTurbulenceProperties(simulationType, model)` writes `constant/turbulenceProperties` and `parseTurbulenceModel` reads it back.
3. **A new field name** (e.g. a transition or v2f variable): add it to `TURBULENCE_FIELD_NAMES`; write a `field<Name>(patches, model)` renderer and its `case '0/<name>'` in `renderSolverFile`; add cases in `turbulenceWallBc`, `inletFieldBc` and `outletFieldBc` (otherwise it silently gets `zeroGradient`); `componentInletBc` / `componentOutletBc` delegate unknown fields to the generic presets; add it to `RESIDUAL_FIELDS` if the chart should order it. `transportedTurbulenceFields` exists twice (`files.service.ts` and `openfoamCase.ts`, different handling of an undefined model): both derive from `turbulenceFieldsFor`, keep it that way.
4. **Defaults**: `kOmegaSST` is the fallback in `scaffoldSolver`, in the three copies of `caseTurbulenceModel` (`files.service.ts`, `boundary.service.ts`, `mesh.service.ts`) and in `SolverSetupWizard` (`useState('kOmegaSST')`). Changing the default means all of them.
5. **Turbulence calculator** (`features/solver/TurbulenceCalculator.tsx`) only writes `0/k` and `0/omega` or `0/epsilon`: a model without those fields gets highlighted seeds but nothing written.

- `apps/api/tests/runnable.test.ts`: unit `renderSolverFile` for the new model (div schemes, keyed solver lines; copy the `kEpsilon` and `laminar` cases) and integration "gate + scaffold" (copy `applies the chosen turbulence model and writes ONLY its fields (kEpsilon, no omega)`): exact fields written, case runnable, second scaffold idempotent, model switch removes stale fields and refreshes wall functions.

## Verify
- `npm run build:shared` (the API tests read `packages/shared/dist`).
- `cd apps/api && npx vitest run tests/solverCatalog.test.ts tests/runnable.test.ts tests/openfoamCase.test.ts tests/boundary.test.ts tests/solver.test.ts`
- `cd apps/web && npx vitest run src/features/solver`
- `npm run typecheck` and `npm run lint` at the root.
- On the Debian server: scaffold a real meshed case, run it a few iterations, check the log has no `FOAM FATAL` (missing div scheme, missing linear solver, unknown BC). Until done, write "to validate on the Debian server" in the changelog.

## Pitfalls
- OpenFOAM.org syntax (`foamRun -solver`, `createNonConformalCouples`) does not exist in ESI v2406; a `controlDict` left at `application foamRun;` (generic skeleton, L7) is never runnable.
- **M18**: a `base` tier solver is "guided" in the UI but receives RANS incompressible files; say so to the user instead of claiming full support.
- **K29**: `renderSolverFile('constant/turbulenceProperties')` always renders `kOmegaSST`; the scaffold uses `renderTurbulenceProperties`. Never call the former for a chosen model.
- Changing a `system/` renderer without updating the `systemNumericsNeedsRepair` markers breaks the gate or the scaffold idempotence (see `solver-and-runs.md` §10).
- Forgetting `TURBULENCE_MODEL_IDS`: the wizard shows the model but the scaffold answers 422 `VALIDATION_ERROR`.
- Forgetting `npm run build:shared`: API tests and `tsc` run against the old catalog and pass or fail for the wrong reason.
- The fake runners of `solver.test.ts` imitate real solver output: a change to `residualParser` or `classifyExit` must be mirrored in their scripted logs.
- LES/DES with a steady solver is only warned in the wizard, not blocked by the API.
